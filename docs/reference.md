# Reference

The commands, session files, page controls and publishing of view-concept. The [README](../README.md) says what the tool is and how to install it.

`skills/explain-concept/SKILL.md` is a copy: the original lives in the author's own skills collection and is synced here by hand. No skill here reads it: each skill is self-contained, and `view-concept` carries the phases it runs.

## How a session works

The skill runs these commands. You don't need to run them yourself.

| Command | What it does |
|---|---|
| `view-concept new "<title>" --slug <slug> [--initial-request "…"] [--kind code --repo … --base … --workflow …]` | creates `~/.view-concept/sessions/<slug>/`; `--initial-request` keeps the user's first message verbatim, `--base` the branch a branch review compares with |
| `view-concept open <slug>` | starts the server (port 5080) if needed and opens the page |
| | `new` and `open` also record the agent that runs them and its conversation (`agent.json`), which side threads run on and fork from; `--agent claude\|codex\|jazz\|command` and `--agent-name` say which when it is not detected |
| `view-concept status <slug> <phase>` | tells the page what the agent is doing; `awaiting-approval`, `awaiting-model` and `awaiting-pr` show the button the user answers with, and `scoping` (the questions asked before the plan is written) shows « Write plan » in the scope block (« Write model » in a branch review or a refactor); in a branch review, `awaiting-answer` while sections of the model are left to write is the writer's **pause**, set by the coordinator when the writer reports one, and shows « Go on » |
| `view-concept question <slug> "<question>" [--option … --option …] [--multi] [--recommended …] [--background …] [--section <id>]` | puts an agent question to the user in the page (`questions.json`), with the answer the agent suggests when `--recommended` gives one, what you need to know to answer when `--background` gives it (shown folded under the question), and its **anchor section** when `--section` gives one (the page shows it at the end of that section once the section is written), and prints its id (`q1`). It sets the phase `awaiting-answer`, except during the phase `scoping`, which it leaves alone: the agent keeps asking without waiting |
| `view-concept anchor <slug> <qid> <section id>` | sets the anchor section of an open or deferred agent question: the section after which it is asked |
| `view-concept reask <slug> <qid> [--text …] [--recommended …]` | asks a **deferred** agent question (one you answered « I don't understand ») again, under the same id, once the section that explains it is written: it is open again, with a new wording or suggestion when given, its background removed (the section above it now explains it), and the phase becomes `awaiting-answer` |
| `view-concept answered <slug> <qid> [--text "<answer>"]` | marks an open agent question answered in the terminal: status `answered`, the answer stored with empty choices, the user's words as text and `from: "terminal"`. It sends no batch, since the agent already has the answer, and leaves the phase alone |
| `view-concept watch <slug>` | prints each comment batch as it arrives and nothing else, meant to run under a background monitor tool (Claude Code's `Monitor`); while it runs it rewrites its heartbeat, `watch.json`, every few seconds |
| `view-concept wait <slug> [--timeout 540]` | for an agent without a monitor: blocks until the next comment batch, prints it and exits; exit code 3 and no output when none arrives in time. Same heartbeat and same cursor as `watch`, so the two can be mixed without losing or repeating a batch |
| `view-concept pending <slug>` | lists comments not yet resolved |
| `view-concept resolve <slug> c3 b2 --reply "…"` | marks comments or whole batches resolved |
| `view-concept change <slug> "<what changed>" [--by planner\|writer] [--cause q3 c7 …]` | appends one change of the model to the change history (`change-history.json`); without `--cause`, the agent made it on its own judgment |
| `view-concept changes [<slug>] [--repo …]` | prints the change history as Markdown bullets, for a PR description's Decisions section |
| `view-concept plan <slug> <file\|->` | replaces the outline, the lexicon or both from a JSON file `{"outline": [...], "lexicon": [...]}`, leaving every other field of `plan.json` alone; it refuses an entry without an id or a title, a repeated id, and a term whose section is not in the outline |
| `view-concept message <slug> "<text>"` | records a terminal message of the user about the feature (`terminal-messages.json`), for the agents that never see the terminal |
| `view-concept implemented <slug> [<change id>]` | records the last change of the model an implementer run took into account (`implemented.json`); without an id, prints it and the changes not implemented yet |
| `view-concept context <slug> --role planner\|writer\|implementer\|reviewer\|thread [--trigger …] [--section …]` | prints the context a branch review's subagent starts from: the initial request, the outline, the lexicon, the recent change history, questions and terminal messages (the 20 most recent of each; every open question), the sections the role needs (the writer and the reviewer all of them, the implementer the modeling part and the sections its trigger names), the trigger's events in full, and once the model is approved, the changes not implemented yet |
| `view-concept check <slug>` | the precedence check: lists every forward reference and early use and writes them to `audit.json` as issues `forward` and `early`, keeping its other entries. Then prints the section problems (see **HTML sections**), which it does not write to `audit.json` |
| `view-concept export <slug>` | writes `~/Documents/Vault/explanations/<title>.md`, with its images and videos in `explanations/<slug>/assets/`, its widgets in `explanations/<slug>/widgets/` and its HTML sections, with their media folders, in `explanations/<slug>/` |
| `view-concept publish <slug>` | publishes the explanation as a published page in the pages repo and prints its link; publishing again replaces the page at the same link. Refuses a code session |
| `view-concept unpublish <slug>` | deletes the published page from the pages repo, pushes the deletion and deletes the publish record |
| `view-concept list` / `stop` / `serve` | lists sessions / stops the background server / runs the server in the foreground |

A session's **workflow** is the skill that drives it: `view-concept`, `view-branch` or `view-refactor`. `new --workflow` records it in `plan.json`, next to the session's `kind`; it defaults to `view-concept` for an explanation and to `view-branch` for a code session, and `view-branch` and `view-refactor` need a code session. The workflow picks the **verdict set** the page shows: `src/view_concept/verdicts.yaml` holds one list of verdicts per workflow, keyed by its name. A session created before workflows existed has none and gets view-branch's set; an explanation gets none.

The **lexicon** of `plan.json` gives each term a **home section** (the section that introduces it), a `definition` (the one-line meaning the plan commits to) and a `tip` (the hover text, which falls back to `definition`). Both are written for the **first-use reader**: someone who has read the sections in order up to the term's home section and nothing after. The **precedence rule** binds them: a term's introducing prose, its `definition` and its `tip` use only terms whose home section is at or before its own. Its two breaches are a **forward reference** (a `definition` or `tip` uses a term introduced later) and an **early use** (a term appears in the prose of a section before its home section; the visible text of an HTML section counts as prose). The hover text also has no location details (files, keys, scripts, section numbers, former names) and does not repeat what other entries define.

The file formats (`plan.json`, `sections/<id>.md` or `sections/<id>.html`, `audit.json`, the comment batch) are described in `skills/view-concept/SKILL.md`; what a branch review adds (`"part": "refactoring"`, the item fields, `"kind": "finding"`, the `approve-model` and `create-pr` actions, the change history, the terminal messages, the context its agents start from) in `skills/view-branch/SKILL.md` and its role files, `skills/view-branch/roles/`. The docstring of `store.py` documents the session directory.

## A branch review

`view-branch` runs a code session on the branch and reviews it through its **model**: the set of concepts the branch introduces or changes (objects, rules, formats, names the code relies on), with their rules and how they fit the existing code. The model lives in the session, in the lexicon of `plan.json` and in the modeling part of the review (the sections that write the model out); it is not stored in the repository.

A **section** is one element of the `outline` list in `plan.json`, with its text in `sections/<id>.md`, or `sections/<id>.html` for an HTML section. A **refactor section** is marked `"part": "refactoring"`: it belongs to the **refactoring part** of a review and shows in the Refactor tab. Every other section is an **explanation section** and shows in the Explanation tab, which a branch review names the Model tab, since there those sections form the **modeling part**.

The **change history** (`change-history.json`) logs every change of the model, one entry each: when, who made it (the planner or the writer), the change in a few words, and what caused it (question, comment or terminal message ids, or the agent's own judgment). `view-concept change` appends one; `view-concept changes` prints the list, which the Decisions section of the PR description is written from. A session written before it has `changes.json` instead, read the same way.

The main session of a branch review only **coordinates**: it routes your events (answers, comments, buttons, terminal messages) to four subagents that start fresh from the session folder (`view-concept context`), one at a time. The **planner** owns the outline and the lexicon during scoping: it drafts them, revises them after each answer and asks the questions they raise. The **writer** owns the modeling part, and the outline and the lexicon with it from « Write model » on. The **implementer** owns the code from « Approve model » on: it makes the code carry the model, and may split its work across helper agents in separate git worktrees. The **reviewer** owns the refactoring part: it checks the code against the model after each implementer run. Your later terminal messages about the feature are recorded in `terminal-messages.json`, since the agents never see the terminal; your first message is the session's initial request, in `plan.json`.

The review runs in two steps, each ending on a page element:

| Step | What happens | Page element |
|---|---|---|
| model consolidation | The planner drafts the outline and the lexicon and asks its scoping questions; after « Write model », the writer writes the modeling part (the model) in the Model tab; the user challenges it, and each change of the model goes to the change history | « Approve model » (status `awaiting-model`), at the bottom of the Model tab, ends the step and starts the implementation |
| implementation | The implementer makes the code carry the model, then the reviewer writes the refactoring part: one refactor section per **item** of the diff (a file, or several files with one job), with its verdict against the model in its item fields, the findings across items, and the **applied changes** (the section with id `applied`: each implementer run's commits and what it could not do). An item judged `diverges` or `move` goes back to the implementer. A change of the model after approval is **not implemented yet** until an implementer run records it (`view-concept implemented`, `implemented.json`); the page marks such changes in the change history and above the Refactor tab | « Create PR » (status `awaiting-pr`), at the bottom of the Refactor tab: the implementer updates the docs, then the PR is opened, for you to review in VS Code |

An item's **item fields**, under `item` in its `plan.json` entry, are its `files`, its `verdict` (one of the keys of the session workflow's list in `src/view_concept/verdicts.yaml`, which gives each one's meaning, its `tone` and where it sends the review, in the review table's order), an optional `batch` (a short label or number), the concepts it `implements`, a one-line `note` and its `relations` to other files (`{to, kind, from?}`, where the optional `from` names which of the item's files the arrow starts from, by default its first). A **finding across items** is a refactor section with `"kind": "finding"` and `"items": [<item ids>]`: a problem between items, such as the same logic in two files. Code that no concept describes is a finding, and the reviewer asks you whether the model should take it in. The steps and the agents' rules are defined in `skills/view-branch/SKILL.md`.

A verdict's **tone** is the colour the page draws it in, one of `ok`, `danger`, `warn`, `alt`, `flag` and `info`. The page has one style per tone, not per verdict, so adding a verdict is one entry in `verdicts.yaml`; a verdict the list does not know is drawn neutral.

## A refactor

`view-refactor` reviews existing code that was written quickly. It cuts the files it is pointed at into items and gives each one a **triage verdict**, from view-refactor's own list in `verdicts.yaml`: `move`, `split`, `merge`, `throw`, `separate-pr` (the item belongs to a different topic, outside this refactor) and `keep`. Once the user approves the triage, the verdicts are applied on the current branch, or the items are grouped into batches, each one a PR reviewed with `view-branch`; an item's `batch` field names its batch. The steps are defined in `skills/view-refactor/SKILL.md`.

## HTML sections

A section is written either in Markdown, `sections/<id>.md`, or as an **HTML section**, `sections/<id>.html`: a self-contained HTML document (its HTML, CSS and JavaScript in one file) which may hold prose and visuals alike, as an artifact on claude.ai does. The file's extension alone says which kind a section is; `plan.json` does not change. A section has one file: when both `<id>.md` and `<id>.html` exist, every reader (the page, `check`, the agents' context, the export, the publish) takes the `.html` file. Where a tool needs the words of an HTML section without running it (the precedence check, the agents' context), it reads its **visible text**: the words written in its file outside `<script>` and `<style>`; text a script draws when the section runs does not count.

**Raw HTML**, HTML tags written straight into a Markdown section among its prose, keeps rendering as before: the page passes it through as it is, so older sessions look the same. An **HTML block** is raw HTML that starts its own paragraph (a line beginning with a tag such as `<div>`, `<svg>`, `<style>` or `<table>`, and everything after it up to the next blank line); **inline HTML** is a tag among the words of a sentence (`<b>`, `<span>`). Tags inside a code block or a Mermaid diagram are not HTML of the section.

The page draws an HTML section in a **section frame**, a sandboxed `<iframe>`: the section is a separate web page drawn inside a rectangle of the page, its scripts run, its styles apply only inside it, and neither it nor the page can reach into the other. It may load from any site (libraries, images, fonts, data), so a section that loads from the web misses what it loads when offline. The frame takes the height of its content and the page's theme (where no page gives one, as in a vault note, the page's default: Catppuccin Latte in light mode, Tokyo Night in dark mode), and a section can paint with the page's colours (`var(--ink)`, `var(--accent)`…). The page's tools work inside it as in a Markdown section: comments and side threads on a passage, change highlights, term underlines and their tips; the section can also be commented as a whole from its heading, and an update puts the change bar on its whole rectangle. Text a script paints into a `<canvas>` is pixels, out of their reach: a figure drawn there is commented as a whole. How the frame works, and why the section is drawn in one, is in [`docs/html-sections.md`](html-sections.md).

An HTML section's **media folder**, `sections/<id>/`, holds the media files the agent produced for it (a manim render, a GIF), which have no web address: the section loads them by a relative address (`<id>/step-1.mp4`). The page serves them at `/s/<slug>/sections/<id>/<file>`, and the published page and the vault export copy the folder next to the section's file.

The **visual rule**, written into each of the three skills, tells the agent when to write a section as HTML rather than Markdown (whenever a section has something to show: a mechanism that runs over time, a structure the reader can explore, a before/after, a mockup of an output, a chart; a Markdown section for an argument, a definition or a rule; a Mermaid diagram for a plain structure in an otherwise prose section), and what an HTML section contains: under 2 MB, embedded media included, a larger image or video loaded from the web or from the media folder; libraries from cdnjs, jsdelivr or unpkg, any other site when needed; as much prose as the agent chooses, knowing its cost there.

`view-concept check` reports four **section problems** besides the precedence problems. They are about how a section is written, not about a word, so they are only printed, for the agent, and never written to `audit.json`, whose entries the page draws as an underline on their term:

| Issue | Reported when |
|---|---|
| `html-block` | a Markdown section holds an HTML block (inline HTML is not reported): « move this HTML block into an HTML section » |
| `two-files` | a section has both `<id>.md` and `<id>.html`: it names the `.md` file the page ignores |
| `too-large` | an HTML section file is over 2 MB, its media folder apart: « move its media to the media folder or the web » |
| `stale-anchor` | a **waiting question** (a deferred question, or an open one with an anchor section) is anchored to a section the outline no longer has, so it would never be asked again: « re-anchor it with view-concept anchor » |

Every session is checked the same way, older ones included; a report changes nothing in how a section renders.

## Publishing

A **published page** is a read-only copy of a session's explanation that anyone can open from a link: one file, `<slug>/index.html`, with its CSS and JavaScript written in (only KaTeX and Mermaid load from the web, as in the page). It shows the title, the date of the last publish and the written explanation sections in outline order, numbered by their position in the outline, with every lexicon term underlined and its hover text shown on hover; light or dark follows the reader's system. It leaves out the plan, comments, side threads, the review pane, the « updated » highlights and the audit underlines. An image a section takes from this machine is copied into `<slug>/assets/` and its link rewritten. An HTML section is drawn in a section frame, as in the page: its file goes to `<slug>/sections/<id>.html`, its media folder next to it; the published page gives the frame its theme, and underlines the lexicon terms inside it and shows their hover text, as the page does. The page is a copy of the session at the moment of the publish: it changes only when you publish again.

The **pages repo** is a public GitHub repository whose GitHub Pages site serves its `main` branch as it is (a `.nojekyll` at its root turns off Jekyll), together with its clone on this machine (`VIEW_CONCEPT_PAGES`). It holds one folder per published session, named by its slug, and nothing else is served: there is no index at the root, so a page is reached only from its link. The link is the site's address followed by `<slug>/`; the address is `VIEW_CONCEPT_PAGES_URL` when set, else derived from the clone's `origin` remote (`https://<owner>.github.io/<repo>/`). Being public, the repository shows anyone its list of folders and, in its history, every page taken down. With no clone, the first publish sets it up with `gh`: it creates the repository (named by `VIEW_CONCEPT_PAGES_REPO`) if it does not exist, clones it, commits `.nojekyll` on `main` when it is empty, and turns on GitHub Pages from `main`.

To **publish** is to build the published page into `<slug>/` of the clone, commit it (`publish <slug>`), push it and write the session's publish record; to **unpublish** is to delete the folder, commit (`unpublish <slug>`), push the deletion and delete the record, after which the link answers 404 once GitHub Pages redeploys. A code session is never published: it cites your repositories, and the pages repo is public. There is no pull before a push: publishing from a second machine fails at the push until you run `git pull` in its clone.

The **publish record**, `published.json` in the session directory, is what a session remembers of its last publish: `url` (the link), `at` (when) and `fingerprint`, a hash of what a published page shows (the title, the published sections and the lexicon). A published session is **out of date** when its fingerprint now differs from the recorded one; comments, threads and highlights do not count, since a published page does not show them. The page reads the record to choose its publish buttons.

## The page

- **Plan / Explanation / Refactor** (left, one at a time): tabs, or the keys `1`, `2` and `3`. In a branch review the Explanation tab is named « model », since it holds the modeling part, the model of the branch. The Refactor tab shows only in a branch review or a refactor that has reached the refactoring part. The page switches to the Plan tab when scoping starts or the plan is waiting for approval, and to the tab of the section being written when writing starts. Otherwise the tab stays where you left it.
  - In a branch review: « Approve model » at the bottom of the Model tab, after the last section of the modeling part, when the model waits for approval (the model is settled and the implementation starts); « Create PR » at the bottom of the Refactor tab once the reviewer has written the refactoring part (the implementer updates the docs, then the main session opens or updates the PR). Draft comments go with either. The page does not switch tabs for them.
  - *Plan*: the scope block (see **agent questions** below), « Approve plan » (when the agent is waiting for it; draft comments go with it), the last revision (in a branch review, the last entry of the change history), the outline with what each section adds (« + comment » on each), the change history of a branch review, and the lexicon. Clicking a section in the outline opens it.
  - *Explanation*: one block per explanation section. Lexicon terms are underlined, and hovering one shows its hover text. Terms flagged by the vocabulary audit, including the forward references and early uses of `check`, get a wavy underline; several notes on one term in a section share one underline, whose hover lists them all. When the agent rewrites a section, what changed since your last batch stays highlighted: the inserted words get a green background, and every changed paragraph, list item or cell gets a green bar in the margin (a deletion only gets the bar). The section heading and its line in the outline say « updated », and the tab shows how many sections were updated. Sending any batch (comments, an approval, an answer) clears every highlight: the text each section has then becomes its **highlight baseline**, so after the agent handles a batch the highlights show what it changed for that batch. « updated · mark read » in the heading clears one section's highlights early. The baselines are kept in `seen.json`, so the highlights survive a reload and show changes made while the page was closed. A section's first text is never highlighted. In a code session, `file:line` citations open VS Code. An HTML section shows in its section frame (see **HTML sections**): term underlines, change highlights, comments and threads on a passage work inside it as in a Markdown section (except text painted in a `<canvas>`), and an update puts the change bar on the whole rectangle.
  - *Refactor*: the refactor sections. At the top, the review table: one item entry per item (its files, a verdict badge coloured by its tone, its batch when any item has one, the concepts it implements with their definitions on hover, the note), the items that need action first and the verdicts counted in the header. Clicking an entry opens its description, the item's section, where comments and threads work as in the explanation. Under it, the structure view, a Mermaid chart drawn from the item fields: one frame per directory, each file outlined in its verdict's tone, files outside the diff greyed out, an arrow per relation, a dashed line per finding across items; the findings are listed under the chart with the items they involve. The applied changes and any other refactor section follow as plain sections. Clicking a refactor section in the plan, or a comment anchored on one, opens this tab and its item entry.
- **agent questions**: an **agent question** is a question the agent puts to you in the page instead of the terminal: the scoping questions, asked before the plan is written (your level, the sense of a word, the goal; in a branch review, the feature about to be implemented), and any later question, because a batch, a model change or a terminal message moved what the session covers. They all live in the **scope block**, at the top of the Plan tab. Each open one is a box: its text, its options (radio buttons, or checkboxes when several may be picked) and always a free-text field. When the agent suggests an answer, the box preselects that option or pre-fills the text, marked « suggested ». Open boxes stack in the order the agent asked them, and the answered and skipped questions fold under them in « answered (N) ». The browser tab title starts with « ● » while one is open. A question asked in scoping may carry a **background**, folded under its text: the mechanism the question is about, as it is today, and what each option keeps and loses. A question asked at the end of a section carries none, since the section explains it. A box has four exits. « Validate » sends your **answer** (the options picked and the text) at once, never as a draft: a batch whose `action` field is `answer`, which the watch prints as `answer to q1 « <question> »: <choices> — <text>`. « Skip » sends « no answer, use your default » the same way (the watch prints `q1 skipped « <question> » (no answer: use your default)`). « I don't understand » sends the text field as a note of what is missing, and ignores the options (the watch prints `q1 unclear « <question> » (…): <note>`): the question becomes **deferred**, folds under « deferred (N) » with the section after which it will be asked again, and the agent makes the model (or the plan) explain what it needs first. When that section is written, the agent asks it again under the same id, and the box shows at the end of the section in the Model tab (the scope block keeps a line pointing to it). « Write plan » leaves a deferred question deferred. Or leave it open: outside a branch review no question blocks the agent, which may add new ones while others are open. In a branch review, the writer writes the model one section at a time and makes a **pause** after a section that opened questions (or whose section question is still open): it writes nothing further until they are answered, skipped or deferred. The page reads the pause from the phase, not from the open questions: the coordinator sets `awaiting-answer` when the writer reports a pause, and the writer's next status ends it. « Go on », under the paused section's boxes and in the scope block in place of « Rewrite model », ends the pause without answering: a batch whose action is `go-on`, after which the writer writes the next sections and the pause's questions stay open. Still open once every section is written, they hold back « Approve model » until each is answered, skipped or deferred. An answer you type in the terminal instead closes the box too: the agent marks it answered (`view-concept answered`), and it folds under « answered (N) » marked « (in the terminal) ». The block's header holds « Grill me », which starts a **grill** (the agent asks about every open decision of the plan, or of the model in a branch review, each with its suggestion, until none is left; « Stop grill » takes its place while it runs, and turns back into « Grill me » when the agent ends the grill or the model is approved), and, while scoping runs or a question is open, « Write plan » (« Write model » in a branch review or a refactor), which ends scoping: the open questions count as skipped, except a section question whose section is not written yet, which stays open until the section is written and shows at its end, and the agent writes the plan (the model in a branch review). Once a plan exists, the button reads « Rewrite plan » (« Rewrite model », once the model's sections are written: a branch review's planner drafts an outline before scoping ends): the agent revises the plan (or the model) with the answers given since, and the watch prints the batch as a rewrite. These three send a batch with the action `grill`, `stop-grill` or `plan`, and the draft comments go with it, as « Go on » does.
- **Review** (right, always visible): the **divider**, the border between the workspace (the tabs) and the review pane, can be dragged to set the pane's width, from 300 px to 70 % of the window; the width is remembered in this browser, and a double-click on the divider resets it. The pane reads like a conversation, oldest at the top. First the sent batches in time order, an answered agent question showing in its place its text and then the answer (« skipped » for a skipped one); then a line « N questions waiting → » while agent questions are open, which opens the Plan tab at the scope block; then the drafts, the note and « Send » at the bottom. The pane stays scrolled to the bottom as content arrives, unless you scrolled up. Select text and click « + comment » to add a draft comment (⌘↵ saves it). Drafts survive a reload. « Send » sends all drafts plus an optional note as one batch. Sent comments show « waiting », then « resolved » with the agent's reply.
- **Threads**: « ask » next to « + comment » on a selection, « ask » on a section, or « ask » in the top bar for a general question. The message you type after « ask » is a **user question**, the counterpart of an agent question: you ask, and a side thread, the conversation it opens, answers. A thread is a separate conversation: its first turn forks the terminal session (`claude -p --resume <id> --fork-session`), so it knows the discussion so far, and the terminal session never sees it. In a branch review it does not fork, since the terminal session only coordinates: its first turn carries the context a subagent gets (`view-concept context --role thread`). Its brief lists the lexicon terms you have read up to the passage (the terms whose home section comes at or before it), and it uses only those, saying anything newer in plain words. It opens in a popover on its passage; a click anywhere else closes it, and a click on the highlighted passage opens it again. A thread with no passage (a whole section, a general question, or a passage since rewritten) gets a chip instead, in the section heading or the top bar. In a question or a reply, Enter sends and Shift+Enter starts a new line. Threads are read-only (Read, Grep, Glob, no MCP). « → batch » adds a draft comment anchored to the thread's passage; its text is optional (without one, the thread's conclusion is the comment), and the batch tells the session which thread it comes from. « Delete » removes a thread no sent comment points to. Each turn re-sends the forked history, so a thread on a long session uses a lot of the subscription's limits.
- **Listening** (top): « ● Agent listening » while a watch runs for the session, « ○ Agent not listening » when its heartbeat is older than 15 s or missing (between a Monitor expiry and the re-arm, or when the agent stopped watching). The « live » dot next to it only says whether the page is connected to the server. A batch sent while nobody listens waits in the inbox, and the page says so: « The agent isn't listening: write anything in the terminal and it will read this batch ».
- **Export to vault** (top): writes one Obsidian note. Exporting again overwrites that note, but never a note you wrote yourself with the same title. The note stays small: images and videos go to files in `explanations/<slug>/assets/`, and each widget (step player, sliders) becomes a `dataviewjs` block that renders it from `explanations/<slug>/widgets/`. An HTML section needs no guessing: its file and its media folder are copied into `explanations/<slug>/`, and under the section's title the note holds a link to the file, which opens the section in the browser as a page of its own in the page's default theme, and a `dataviewjs` block that draws the section in a section frame inside the note, in the page's default theme for the mode Obsidian is in. The note does not hold the section's text, so Obsidian's search does not find it. The widgets and the HTML section frames run in Obsidian only with the Dataview plugin and its « Enable JavaScript Queries » setting on; without it the block shows as code.
- **Publish** (top, next to « Export to vault »; hidden in a code session): follows the publish record. « Publish » when the session was never published: it publishes, then copies the link and shows it. « Published <date> » when the published page is up to date: a click copies the link. « Republish · changed since <date> » when it is out of date: a click publishes again at the same link. « Unpublish » shows next to it once published, asks to confirm, then takes the page down.

The page redraws when a file changes (server-sent events, checked every 0.4 s). KaTeX and Mermaid load from jsdelivr. When offline, maths shows as TeX source, diagrams as code, and an HTML section that loads from the web misses what it loads. `?static` in the URL turns off live updates (for headless rendering).

## Agents

The skills run on whichever agent the user works in. Only the side threads need the agent itself, because each turn is a headless process the server starts. `new` and `open` record the agent in `agent.json`: Claude Code (`CLAUDE_CODE_SESSION_ID`) and Codex (`CODEX_THREAD_ID`) announce themselves, and Jazz (`JAZZ_AGENT_PROCESS`) does too but is also passed `--agent jazz --agent-name <agent>` so threads know which agent to run.

| Agent | A side thread's turn | First turn | Read-only through |
|---|---|---|---|
| `claude` | `claude -p --output-format stream-json` | `--resume <main> --fork-session` | `--tools Read Grep Glob`, `--permission-mode dontAsk` |
| `codex` | `codex exec --json -` | `codex exec fork <main>`, then `codex exec resume <thread>` | `sandbox_mode="read-only"`, `approval_policy="never"` |
| `jazz` | `jazz --no-tui run --agent <name>` | none to fork: each turn restates the session's location and the thread so far | `--approval-policy read-only` |
| `command` | the program in `VIEW_CONCEPT_AGENT_COMMAND` | same as `jazz` | whatever the program enforces |

A program for `command` receives the prompt on stdin, prints the answer on stdout (streamed into the reply as lines arrive) and exits 0; any other exit code shows its last output as the thread's error.

The comment channel is also per agent: `watch` where there is a background monitor tool, `wait` everywhere else (see the commands above).
