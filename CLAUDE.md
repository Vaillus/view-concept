# CLAUDE.md

A local web page (FastAPI + vanilla JS) for four skills kept in `skills/`: `view-concept` (an explanation in six phases), `view-branch` (a branch review), `view-refactor` (a triage of existing code) and `view-docs` (a docs review: a repo's docs on a scope, with no branch to model). `skills/` also holds `write-readme`, which writes a folder's README from its code, or rewrites an existing one, in the terminal with no page and no session. Each skill is self-contained: it carries every rule it follows and never sends the agent to read another skill, so a rule shared by two skills is written in both. The one exception is the **rewrite request** (the `rewrite-readme` action): to act on it, view-branch's implementer and view-docs read `skills/write-readme/SKILL.md` and follow it for that one README. A session records its workflow, the skill driving it, in `plan.json`; the workflow picks the verdict set the page shows, one list per workflow in `verdicts.yaml`, where each verdict carries the `tone` the page colours it with. The skills (`skills/<name>/SKILL.md`, written for any agent: Claude Code, Codex, Jazz) write session files. The page renders them and sends comment batches back through an inbox file, which `view-concept watch` (under a background monitor) or `view-concept wait` (blocking, one batch per call) hands to the agent session. Usage is in the README; commands, session files and page controls are in `docs/reference.md`.

- The file contract (`plan.json`, `sections/` (`<id>.md`, or `<id>.html` for an HTML section, with its media folder `<id>/`), `audit.json` (which `view-concept check` also writes, issues `forward` and `early`; its section problems are only printed), comment batch format, `questions.json` (status `open`, `answered`, `skipped` or `deferred`, the optional `recommended` answer, `background` and anchor `section`, the `unclear` notes of a deferred question, an answer's `from: "terminal"` when `view-concept answered` closed it without a batch, `view-concept anchor` and `reask`), the `awaiting-answer` phase of an agent question (not set during the `scoping` phase, which a question leaves alone), the `answer` action of the batch that answers or skips it (a skip's entry is `{question, skipped: true}`, an « I don't understand »'s `{question, unclear: true, note}`; any entry's `threads`, the side threads opened on the question), `view-concept status`'s run set (`writing --section`, repeated) and scoping done mark (`scoping --done`), the `plan` (ends scoping, marking open questions skipped, except a section question whose anchor section is not written yet), `grill` and `stop-grill` actions, and the `go-on` action that ends a branch review writer's pause (the `awaiting-answer` phase while sections of the model are left to write), leaving its questions open) is shared with the skills, `skills/view-concept/SKILL.md`, `skills/view-refactor/SKILL.md`, `skills/view-docs/SKILL.md` and, for what a branch review adds (`"part": "refactoring"`, the applied changes section `applied`, the to-do list section `todo` (written by the writer with the model, shown first in the code tab), the item fields under `item` (with the optional `batch`), `"kind": "finding"`, a lexicon entry's `kind` (`core` or `peripheral`, the term kind only the agents see; same key name as the finding's, a different object), the `awaiting-model`/`awaiting-docs`/`awaiting-pr` phases, the `approve-model`/`write-docs` (with its `then_pr` flag: « Write docs and create PR »)/`create-pr` actions, the `write-lexicon` action (« write repo lexicon », refused once `.agents/lexicon.md` exists) and the `rewrite-readme` action (a rewrite request: its `path`, a `README.md` of the doc set, printed after the action in the batch), both held for the doc pass when sent before it, `doc-set.json` (`view-concept doc-set`: the doc set in the write order, each doc's path, reason, minor class with its diff size and a README's failure indicator, and the docs the user removed), `stale.json` (`view-concept stale`: the stale passages the reviewer flags after the doc pass), `missing-facts.json` (`view-concept facts`: the missing facts of a README rewritten in full, and the `(doc <path> · fact <id>)` anchor of a comment on one), the `doc:<path>` and `doc:` (alone: the doc set list; no section id starts with `doc:`) comment anchors (printed `(doc <path>)` and `(doc set)` in a batch), `change-history.json` (`view-concept change`), `terminal-messages.json` (`view-concept message`), `implemented.json` (`view-concept implemented`: the last model change an implementer took into account; the changes logged after it are not implemented yet), `code-map.md` (where each concept lives in the code: the planner writes it, the implementer updates it, every context loads it), `request.md` (`view-concept request`: the request transcript, the whole conversation that led to the review, read whole by the planner and the writer, by path by the other roles), the `rewrite` flag of a `plan` batch, `plan.json`'s `initial_request`, `base` and `pr` (`view-concept pr`), an outline entry's `earns` (one sentence of at most 200 characters in every skill) and `overview` flag, and the context its agents start from (`view-concept context`, `context.py`)), `skills/view-branch/SKILL.md` and its role files in `skills/view-branch/roles/`; the doc set, the stale passages, the missing facts, the doc comment anchors, the `write-lexicon` and `rewrite-readme` actions (run at once in a docs review), `plan.json`'s `reference` (`view-concept reference`: a docs review's reference model, `{slug, reason}`, a branch review of the same repo; `--candidates` lists them) and the `awaiting-pr` phase of a docs review are shared with `skills/view-docs/SKILL.md`; The repo lexicon (`.agents/lexicon.md` at the repo root: a `# <repo name>` title, a `## Reader` part holding the reader line, the field the docs' reader knows, then a `## Terms` part, one `**Term**:` and its definition per entry) and the folder lexicons (the same file and format below the root, for the terms only the folders under it share; the closest one on a path wins) are shared with `skills/write-readme/SKILL.md`, the view-branch role files (`writer.md` and `implementer.md`: the doc set's fifth rule; `planner.md` and `planning-rules.md`: read first), `skills/view-branch/SKILL.md`, `skills/view-docs/SKILL.md` and `skills/view-concept/SKILL.md` (Phase 2); `store.py` and `app.js` name its path `REPO_LEXICON`. `verdicts.yaml` and the session workflow are shared with `skills/view-branch/SKILL.md`, `skills/view-refactor/SKILL.md` and `skills/view-docs/SKILL.md`. Change them together. `agent.json`, `threads/` (`threads.py`), `watch.json` (the watch's heartbeat, which the page shows as « Agent listening »), `seen.json` (the highlight baseline: each section's text at the last batch or « mark read », and each doc's under `doc:<path>`), `drafts.json` (the drafts and the general note, shared by every page open on the session, on any device) and `published.json` (the publish record: link, time, fingerprint) belong to this repo alone (`agents.py` holds what differs between agents); the skills only see the thread line of a batch comment.
- `static/reader.js` (the published page's script) mirrors functions of `static/app.js` (term underlining, maths, Mermaid, the tooltip): change them together.
- Styling uses the omarchy-terminal-skin tokens only (`themes.css` and `terminal.css` are copies from the skill; don't edit them here).
- Lint, format and type-check must pass: `uv run ruff check --fix . && uv run ruff format . && uv run ty check .`, then `uv run pytest`.
- Never add AI attribution to commits or PRs.
